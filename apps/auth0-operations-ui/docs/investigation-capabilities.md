# Investigation capabilities and gaps

This inventory describes the checked-out Auth0 node and LoginLens planner, not a live tenant verification. All tools use the existing RocketRide `tool_auth0_1` and `client.tool` path. Successful execution still depends on engine configuration, tenant entitlement and granted Management API scopes. The node's [README](../../../nodes/src/nodes/tool_auth0/README.md) and decorated schemas in [IInstance.py](../../../nodes/src/nodes/tool_auth0/IInstance.py) are authoritative for exact bounds, nullable fields and errors. Outputs below omit the common `success` and error envelope.

## Classification and questions

The deterministic classifier accepts a triggered rule and its supporting events. It selects a primary classification and can add secondary classifications when the supporting events meet the stated grouping thresholds. It retains severity, rule, evidence, time window and limits. The planner receives labels, reasons, questions and sanitized event types and times. These are heuristics and questions, not attack attribution.

| Classification | Questions and currently available evidence |
| --- | --- |
| Repeated account failures | Is there an observed common account or source group? Could stale credentials explain it? Event lookup and tenant protection settings help; account-specific checks are blocked. |
| Potential password spraying | Do multiple account groups share a source within the observed window? Could shared egress explain it? Group counts and tenant-wide event and protection reads help; group identities and origin history are unavailable to the planner. |
| Geographic anomaly | How does activity compare with earlier tenant traffic? Could network geolocation, a proxy or traffic volume explain it? Coarse location in the initial snapshot and bounded tenant-wide history help; history results are not a verified geographic baseline. |
| Authentication failure spike | How do failures and total activity compare with a covered prior window? Tenant-wide history and recent events help, subject to coverage. |
| Protection-related activity | Was a protection event observed and what settings are currently enabled? The node supports protection event types and settings. The current dashboard normalizer does not emit protection events as anomalies. |
| Possible configuration issue | Are failures concentrated in a particular application or connection, and what diagnostic is available? The dashboard has application names but the node deliberately limits event descriptions and connection configuration. There is no configuration-issue detection rule today. |
| Unknown or insufficient evidence | Which event and time are available, and what must be checked next? Unknown rules or empty evidence remain unclassified. |

The detector also emits protection activity for Auth0 `limit_wc`, `limit_sul` and `limit_mu` events. It attaches a protection event to one overlapping anomaly only when a returned account or source group matches; otherwise it reports a separate signal. A protection event does not establish an attack. Configuration categories do not create alerts on their own. Live volume and rate baselines are suppressed because query exhaustion cannot prove retention or indexing coverage. A missing signal is not a negative result.

## Local source analysis

Every graph containing selected failures includes a local snapshot analysis of anonymous source groups. It reports the number of selected failures, grouped and missing sources, distinct groups and the largest group. No raw IP addresses are retrieved or sent to the model. Group IDs are local to the loaded retrieval; shared egress can group unrelated users, and missing source data limits conclusions. The model receives only the aggregate results.

## Read-only tool inventory

Status **planner** means the bounded adapter exposes it when the relevant scope is granted. **Restricted** means implemented in the node but not exposed to the anomaly planner; this can be due to unresolved evidence-bound identity, privacy, relevance or lack of a reviewed adapter. Some are independently usable in the existing exact-account investigation. All identifiers are supplied by the caller to the node; they are not tenant-authorization proofs.

| Tool | Purpose, inputs → output | Scope | Planner status and classification relevance | Identifier |
| --- | --- | --- | --- | --- |
| `search_authentication_history` | UTC `start,end` → sanitized events, count, pages and coverage, at most five pages | `read:logs` | Planner: anomaly or preceding 24-hour window; spike, geography and general context. Tenant-wide, not account-specific. | No raw identity |
| `search_logs` | optional `event_type,limit,analytics` → one sanitized event page and count | `read:logs` | Planner: selected failure or protection type, latest page; repeated failures, spraying, spike and protection context. May not cover the anomaly period. | Event-type reference; no raw identity in analytics mode |
| `get_log_event` | `log_id`, optional `analytics` → sanitized event and fixed diagnostics | `read:logs` | Planner: verify a selected failure event; all supported classifications. | Event ID from current in-memory snapshot; not server-authorized provenance |
| `get_brute_force_settings` | no inputs → enabled, mode, attempts and shields | `read:attack_protection` | Planner: repeated failures, spraying and protection context; current tenant configuration. | None |
| `get_ip_throttling_settings` | no inputs → enabled, shields and login/signup limits | `read:attack_protection` | Planner: spraying, geography, spike and protection context; current tenant configuration. | None |
| `search_users` | exact `email`, optional `limit` → matching users and count | `read:users` | Restricted: repeated failures and account resolution. Requires trusted identity and operator authorization. | Email |
| `get_user` | `user_id` → filtered profile, connections and administrative block | `read:users` | Restricted: repeated failures and account context. | User ID |
| `get_user_logs` | `user_id`, optional `limit` → one page of sanitized events and count | `read:logs_users` | Restricted: repeated failures and account baseline; no date parameter. | User ID |
| `get_user_blocks` | `user_id` → brute-force block records and count | `read:users` | Restricted: account protection; separate from administrative block. | User ID |
| `get_connection` | `connection_id` → ID, name and strategy | `read:connections` | Restricted: configuration context; output excludes connection options. | Connection ID |
| `get_connection_clients` | `connection_id`, optional `limit,cursor` → client IDs, count, next cursor | `read:connections` | Restricted: connection/application configuration context. | Connection ID and optional cursor |
| `list_connections` | optional `page,limit` → connection page and count | `read:connections` | Restricted: configuration inventory; no evidence-bound link from an anomaly or reviewed planner adapter. | None |

| `list_roles` | optional `page,limit` → tenant roles and count | `read:roles` | Restricted: access inventory is not sufficient evidence of a login cause. | None |

| `list_organizations` | optional `limit,cursor` → organizations, count and next cursor | `read:organizations` | Restricted: organization inventory lacks an anomaly binding. | Optional cursor |
| `get_organization_members` | `organization_id`, optional `limit,cursor` → members, count and next cursor | `read:organization_members` | Restricted: unrelated member enumeration is unnecessary for authentication anomaly analysis. | Organization ID and optional cursor |

The planner adapter in `src/lensPlan.ts` is manually maintained. `registryInputs` is checked against the node's decorated metadata in `test_loginlens_planner_adapter_matches_node_input_contracts`; it is not runtime discovery. The AI proposes only bounded references and periods. The app validates up to six calls, four dependency levels, supported operations and evidence references; approval precedes execution. It binds selected event IDs and time windows in the client. The engine's tool call remains subject to its existing authorization and configuration. Browser-held event references do not establish membership or ownership.

## Prioritized capability gaps

| Priority / complexity | Classifications and unanswered question | Existing partial capability and gap category | Proposed investigation capability and permissions | Security and privacy |
| --- | --- | --- | --- | --- |
| P0 / high | Account failures, spraying, geography: which account is associated with this event? | `get_log_event` and user tools exist; **implemented but blocked** by the unverified tenant and evidence-ownership contract. Some Auth0 events omit `user_id`. | Establish a RocketRide-authenticated, server-enforced investigation context that resolves an authorized event to only the user operations required. Relevant scopes include `read:logs`, `read:users`, `read:logs_users`. No new node method is proposed until the boundary is verified. | Check current principal, tenant/integration and event ownership on every operation; protect against forged references, revocation and cross-tenant access; minimize returned identity and LLM input. |
| P1 / medium | Spraying and repeated failures: do events share a source and how many accounts were affected over time? | Analytics returns per-retrieval source and account groups; **missing parameters/fields** for a covered cross-window source aggregate and **authorization restriction** on raw identities. | Review an evidence-scoped aggregate query with bounded time and count outputs, potentially extending history; `read:logs`. Confirm fields actually present before designing it. | Never return raw IP/email to the model; limit small-group reidentification and prevent arbitrary source probing. |
| P1 / medium | Geographic anomaly and spike: was there a meaningful change against prior behavior? | `search_authentication_history` provides bounded tenant-wide counts; **missing fields/parameters** for location-scoped aggregates and longer covered baselines. Retention and pagination limit completeness. | Evaluate a bounded coarse-location/time aggregate and coverage metadata using `read:logs`, or an authorized tenant-isolated Log Stream for sustained history. | Network location is approximate and may represent a VPN or proxy; avoid individual location profiling and define retention. |
| P1 / medium | Protection activity: did protections trigger during this window? | The node and planner support protection event types. **Authorization and evidence limits** prevent reliable account-level attribution. | Evaluate trusted evidence-bound account checks after the identity contract is verified; `read:logs`, `read:users` and `read:attack_protection` as applicable. | A protection event or setting alone does not prove malicious activity or current account state. |
| P2 / medium | Configuration issue: which application or connection is implicated, and is its configuration responsible? | `get_connection`, `list_connections` and `list_applications` exist; **implemented but blocked** bindings and **insufficient response fields**. Diagnostics are fixed/sanitized. | Review an evidence-bound connection/application lookup and a minimal allowlist of relevant nonsecret fields, subject to `read:connections`, `read:clients`, `read:logs`. | Treat names and descriptions as untrusted, exclude credentials and metadata, enforce tenant ownership. |
| P2 / medium | Unknown evidence: why did a specific login fail? | Fixed descriptions and event type provide limited clues; **insufficient response fields** and possibly **unavailable underlying data**. | Evaluate which Auth0 diagnostic fields exist for the event type and whether a sanitized allowlist is supportable with `read:logs`. | Auth0 details may contain identifiers, tokens or attacker-controlled text; use strict field allowlists. |
| P2 / high | Geography and spraying: was the actor physically present at a location or malicious? | IP geolocation and pattern heuristics are indirect; **unsupported by available data** for establishing physical presence or intent. | Corroborate through separately authorized telemetry and human review; no Auth0 scope alone proves either. | Avoid presenting a network origin as a person's physical location or a heuristic as a confirmed attack. |

## Minimum identity boundary

Before enabling account or connection bindings, platform owners must establish and verify the authenticated principal, current tenant membership and permissions at a trusted server-side boundary, the chosen Auth0 integration's ownership, and event-to-tenant ownership for each investigation. The boundary must reject forged, stale and cross-tenant references, recheck revocation, bind resolved identifiers to an approved investigation and minimize outputs. Tests must include missing identifiers and concurrent or revoked access. The existing [identity investigation](architecture/identity-contract-investigation.md) explains what is not yet established.

The contract must be provided by the RocketRide engine's authenticated request/task authorization layer or a supported engine-side app handler that can authorize the `client.tool` execution. The browser shell's `useAuthUser()` result and the Auth0 node's configured M2M credentials do not by themselves establish this association. The trusted component must bind the authenticated RocketRide principal and current organization membership to the authorized Auth0 integration and dataset, issue or retain server-owned investigation evidence references, resolve only references belonging to that authorized context, enforce the approved read-only operation and arguments, and recheck membership and evidence ownership on execution and result access. It must define expiration, revocation and concurrent changes. The node can then consume a permitted identifier through the existing tool path; neither a caller-supplied tenant ID nor a browser-held event ID is proof of access. The checkout does not establish which deployed implementation provides these guarantees.

## Verification and limitations

The planner's structured findings cite successful tool steps and separate observations from conditional explanations. Schema and citation checks do not prove that generated prose is entailed by evidence. Failed or skipped steps are missing evidence, and partial history does not establish absence. Reviewers should compare each finding with the graph and source results. No live Auth0 or Gemini verification is claimed; follow [live verification](loginlens-live-verification.md) for an authorized development tenant.

The offline `test/findingsEvaluation.test.mjs` rubric covers an unknown-cause failure, conflicting protection settings, a failed evidence step and an unknown account. For each scenario a scripted acceptable finding passes a scenario-specific quality rubric, and a deliberately unsupported but schema-valid and cited finding fails that rubric. Malformed JSON is tested separately as a schema failure. These hand-authored cases test the evaluation mechanism only; they do not measure Gemini's accuracy, detect all hallucinations, or add a production truth verifier.
