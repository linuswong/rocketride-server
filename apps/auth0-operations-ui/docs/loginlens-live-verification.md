## Architecture and limits

When a parsed planner graph is rejected, the sanitized planner diagnostics report the first failing constraint, its JSON path, expected constraint and actual value type. They also include a bounded outline of up to six step shapes with recognized tool names and binding presence. Model prose, unknown tool names, step IDs, dependency values, event identifiers and raw output are not retained in this outline. A diagnostic explains the validation failure; it does not repair the proposal or authorize a retry.

The dashboard calls the Auth0 node's `search_authentication_history` through `client.tool` on the existing investigation pipeline. The node uses its existing Management API client and a bounded date query, then returns sanitized events and retrieval status. The app normalizes and deduplicates the response, aggregates metrics, and runs deterministic rules. An exhausted query is still subject to Auth0 retention, search indexing and offset pagination during concurrent ingestion. Partial and unavailable results must be treated as incomplete.

The planner uses a fresh, direct RocketRide chat-to-Gemini task in `planner.pipe`; it has no agent or Auth0 tools. It receives an application-maintained allowlist of five node methods plus the local source-group analysis and up to 20 sanitized event references. It does not dynamically discover tool schemas. A node test checks the adapter's input fields and output assumptions against the node's decorated tool metadata. The executor validates proposals and calls the verified Auth0-only telemetry task only after user approval. Graph execution does not invoke a model. The graph reflects application-observed results. Separately authorized AI findings receive successful sanitized observations and must cite a successful node. Schema validation checks shape and citations, not whether model conclusions are factually entailed.

The analytics response deliberately omits raw account IDs and IPs. Consequently, account-specific tools such as `get_user_logs` cannot safely receive an identifier from the planner. Some failure events have no user ID at all. In addition to `get_log_event`, `get_brute_force_settings` and `get_ip_throttling_settings`, the planner can request `search_authentication_history` for the anomaly window or an equal-length preceding window and `search_logs` for the newest page of the selected event type. Both return tenant-wide activity; their aggregate counts do not establish a relationship to the selected account or source. The former can be partial, and the latter may be outside the anomaly window. Anomaly timestamps and event references are selected in the browser from the current snapshot, not independently authorized provenance tokens. A browser check does not establish server-side tenant membership or prevent a modified client from issuing its own tool calls. Deeper account-specific investigations require a verified RocketRide authorization boundary and evidence-bound identity resolution; until then these tools remain unavailable to the planner.

4. If an anomaly is present, compare its rule, time window, counts and evidence to the returned records. Choose **Propose AI investigation** only when sending the displayed sanitized categories and times to the configured Gemini provider is authorized. Review the tool names, referenced events, purposes and dependency edges before approval.
5. Approve the reads, inspect each graph node and compare its outcome with an independent Auth0 view. Check failed and skipped nodes. Review each AI finding against the cited tool evidence and uncertainty. Confirm that proposed remediations require human review and that no write operation is offered.
6. Record sanitized pass/fail results, provider profile, scope and coverage status. Do not store credentials, raw events, account identifiers or model payloads in a test report. If the engine has an older node or reused task, restart it before repeating.

Offline tests do not call Auth0 or a model provider. No live success should be reported without completing the corresponding steps against the designated tenant and provider.

## Planner response diagnostics and request accounting

The direct planner requests one JSON graph as text (`expectJson: false`), so RocketRide does not perform JSON repair retries. The app accepts one answer from the SDK `result_types` envelope containing either one JSON object or one complete JSON code fence, then applies the existing tool allowlist, argument bindings, reference and dependency validator. Prose containing embedded JSON is rejected. Invalid responses never enable graph execution. A valid schema is not proof that the model's claims are accurate. Gemini schema-constrained generation is not exposed by this node path.

The optional `maxProviderAttempts: 1` node setting reserves one attempt under a lock immediately before `generate_content`. Provider failures consume the attempt, the SDK transport is configured for one attempt, and bounded mode declines further retryable calls. Save-time validation skips its independent provider probe in bounded mode so it consumes zero attempts. The counter is per Gemini node instance in one task; separate tasks each receive a new budget. This is not a monetary spending cap. The task and engine must run the updated node implementation; the catalog field check guards older catalogs but does not attest to a mismatched node binary or multiple node instances. Verify the deployed engine package and test its task isolation before authorizing live use.

The sanitized diagnostics include an app-generated correlation ID, configured provider/profile, app chat dispatch status and app-session dispatch count, response/envelope type and length, JSON parse status, graph validation status, and safe error category. They contain no response body, event evidence or credentials. App dispatch counts and optional RocketRide token metrics are not confirmed provider or billing records. Check authorized provider-side usage/billing records where available. Client timeouts do not ensure remote cancellation.

The older agent-based planner could reach a source-estimated 305 attempts across waves, JSON retries, network retries and synthesis; that estimate does not describe the new direct planner. The separate account-analysis pipeline retains its existing retry behavior.

The prior malformed response was observed at the app's JSON parsing boundary after an answer was extracted; no answer body or finish metadata was retained, so its precise cause and the earlier generic Auth0 error remain unknown. No live planner success is established by offline tests. Obtain fresh authorization with an acceptable request budget before another live test; do not execute a proposed graph until its human review and approval.
