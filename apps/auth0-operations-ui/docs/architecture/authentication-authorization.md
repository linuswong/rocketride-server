# Authentication and authorization design

Milestone 6 reviewed actual shell, SDK, OSS authentication and account routing. See [identity investigation](identity-contract-investigation.md). No supported SupportPilot-audience identity and current-membership contract was established, and the SaaS implementation is outside this checkout. No deployed or mock HTTP API is claimed. `backend/design/contracts.ts` expresses requirements only and must not be used as authentication. Actual API-boundary attacks and real-provider verification remain blocked.

The operator is the shell user, not the Auth0 customer being investigated. `useAuthUser()` exposes a connection result to React, but browser state, an organization ID, a customer email or a resource ID is never a backend authentication assertion. No supported token-exchange and membership-verification contract for a separate SupportPilot service was established in this checkout. Until one is selected and independently verified, production access and persistence remain blocked.

A future service must validate an authenticated session against its issuer, audience, expiry and revocation policy, resolve the principal and current membership from a trusted authority on every operation, and reject missing or stale membership. It must treat requested organization IDs as selectors and verify membership; resource ownership comes from server records. One minimal operator role can list/create/read/update tickets, start investigations, read investigations and evidence, and create/edit drafts within its organization. Archive/delete and retention administration require an explicit separate administrative permission. Deny by default. All reads, updates, links and deletes must authorize both organization and resource; evidence requires its investigation and ticket to belong to the same organization. Investigation-to-ticket binding is immutable or atomically revalidated, never inferred from email. Use uniform not-found/denied responses to limit enumeration.

A start request must authorize the ticket and chosen integration before invoking an engine; an opaque server-generated operation ID and idempotency key should identify the attempt. Establish how to reconcile an unknown outcome before allowing retries. Permission revocation must also govern result retrieval. Server-side transactions and ownership constraints must close check/use races; the test harness does not implement those production guarantees.

Threats and controls: cross-tenant exposure and guessed IDs require server-side scoped queries and parent checks; leaked credentials require engine-managed least-privilege secrets and verified isolation; evidence exfiltration requires minimization, audited access, encryption and export limits; prompt injection requires treating retrieved text as untrusted, no model-authorized actions, and human review; stale authorization requires current membership checks and bounded sessions; incorrect linking requires authoritative ticket/investigation IDs, never email equality; unsafe retries require idempotency and reconciliation; unauthorized model sharing requires explicit consent and a verified provider/data policy; sensitive retention requires configured expiry, deletion, backups and audit controls. All remain design requirements, not demonstrated production controls.
