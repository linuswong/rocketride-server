# Target architecture

Milestone 6 leaves the identity decision gated: see [identity investigation](identity-contract-investigation.md) and [backend design](backend-design.md). The new SQLite schema is a test-only experiment; no connected frontend, production database or server is implemented.

The shell supplies identity, connection and host layout. Presentation renders typed investigation state; orchestration validates a subject, invokes supported reads and records observations; normalization validates external responses and selects permitted evidence fields. A diagnosis is an unverified interpretation, never evidence or permission to act. Use tenant- and user-authorized server storage only after its isolation and retention guarantees have been verified. Do not store customer records in browser local storage as a substitute for access control.

The support demo separates ticket types and validation (`support/domain.ts`), a scoped in-memory repository (`support/repository.ts`), deterministic classification, article lookup and drafting (`support/workflows.ts`), and React presentation (`SupportPlatform.tsx`). This is a development-only slice: a browser-provided scope cannot enforce tenant authorization. Replace the repository with a server-authorized implementation before using real records. The graph remains the existing Auth0 workspace; only a fixed fictional account may be linked in the support demo. Live linking needs server-verified ownership and permissions.

To add a workflow, define its input, output, evidence and uncertainty in the domain, implement a bounded provider behind an interface, add deterministic fixtures and failure tests, and add a route in the support view. Introduce a RocketRide pipeline only when the workflow needs independent engine execution; verify nodes and schemas against the target engine. A provider must not gain authority to send messages or modify accounts merely because a model requested it. See `support-platform-audit.md` for storage and identity findings.

## Investigation workspace redesign

The inbox leads with tickets; New Ticket opens a dedicated creation view. The investigation screen combines compact fictional ticket context, a read-only React Flow graph, an accessible step list, a four-view inspector and an independent diagnosis. Linked fictional records are retained in memory for the session, keyed by investigation ID; switching tickets remounts the workspace. The graph derives from the same validated investigation as the inspector and diagnosis. Legacy warning states are presented as completed execution with a separate diagnostic warning. Workflow edges are configured dependencies and calls are observed in the application; engine invocation IDs and retries are unavailable. See [investigation workspace](investigation-workspace.md) for boundaries and tradeoffs.

## Milestone 5 boundary

See [platform capability audit](platform-capability-audit.md), [authentication and authorization](authentication-authorization.md), and [persistence design](persistence-design.md). Proposed shared contracts and a Node-only authorization model are implemented, but the shell identity cannot yet be validated by an independent SupportPilot backend. No production persistence, authorization, migration, or network API exists. The existing fictional repository and investigation state remain browser memory only. Any real backend must perform authorization itself, including parent ownership and current membership, and prove isolation with integration tests against its real identity and database.
