# Support workflow audit

The existing shell owns the SDK connection and exposes `useAuthUser()` with `userId` and `organization?.id`; `App` already remounts on identity or connection changes. The Auth0 graph, field filtering and direct tool calls can be reused. The current `.pipe` is a real Auth0 workflow and the separate model pipe provides optional interpretation. Ticket classification, tiny fictional-document search and deterministic draft assembly do not require an engine pipeline: packaging them as pipelines would introduce network and provider dependencies without an independently executable production workflow.

The documented shell workspace and `client.fs*` storage are durable per signed-in user on the connected server, offer deletion, and use last-writer-wins workspace updates. The reviewed docs do not establish shared organization-level record authorization, per-ticket access control, concurrency, audit or migrations. They are therefore not selected for shared customer records. Organization identity in the browser is not proof of authorization. A real service must derive the principal and organization from authenticated server context, authorize every operation and record, implement optimistic concurrency, encryption, retention/deletion, audit and versioned migrations. Use the established RocketRide APIs only when their enforcement is verified.

The first implementation is a fictional, memory-only support workspace. Its repository accepts an explicit scope and checks it on every operation, including links; this is a correctness boundary in one JavaScript process, not a multi-tenant security boundary. A malicious browser can change its own memory. Do not put real tickets or customer evidence into it. Link the offline investigation only to the designated fictional fixture subject and ticket, by generated IDs, never by email alone. Live investigation linking requires a server-authorized identity binding and is deferred.

The existing mocked tests and build pass. A running local engine and authorized development credentials are not established. The guarded harness is retained for a separately authorized test; mocks are not live verification.
