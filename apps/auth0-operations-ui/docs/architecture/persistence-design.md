# Persistence design

## Milestone 6 experiment

`backend/design/001_sqlite_experiment.sql` is a non-deployable SQLite schema experiment, not production storage or a migration runner. It models organizations, tickets, investigations and minimal evidence references with composite ownership foreign keys and an immutable investigation binding. Foreign keys must be enabled on every SQLite connection; this schema cannot enforce identity or permissions. Its version column requires a transactional compare-and-update in a future repository. Idempotency, audit, retention, encryption, concurrent revocation and a migration/rollback process are not implemented. No drafts or raw logs are stored. Tests exercise constraints in memory and reopening a temporary database file. SQLite on a durable local volume could support development or one carefully operated instance; PostgreSQL is a stronger candidate for concurrent multi-instance hosting. Neither is selected for production until deployment ownership and isolation are known. Backups must be encrypted and restore-tested, with deletion and backup expiration agreed before use.

No storage option is production-approved. RocketRide workspace/files are convenient and durable in supported deployments, but the reviewed contract does not establish shared organization-level per-record authorization, concurrency, or retention. A dedicated minimal service can enforce the policy and use a managed transactional database, at the cost of hosting, identity integration, migrations and operations. A directly accessed managed database still needs a trusted identity mapping and independently verified row policies; a browser-supplied org ID is insufficient. Selection of a specific vendor, pricing and deployment model is deferred until identity and isolation are proven. Recommend the minimal trusted service plus a managed transactional store only if a verified platform service cannot satisfy the same controls. The operator or marketplace provider must explicitly own hosting, credentials, backups and deletion; that responsibility is not yet assigned.

`src/support/contracts.ts` sketches logical organization, ticket, investigation, evidence and draft records and read contracts; it is not a runtime schema or public API. Existing browser `MemoryTicketRepository` is fictional only. `test/boundary-harness.mjs` is an in-memory deterministic authorization model run in Node, not a network server, production repository, session verifier, migration or durable database. It rechecks a simulated membership for every operation and verifies parent ownership; its tests demonstrate the policy only in that model.

A real implementation must validate all input on the server; derive org ownership from the authorized context; enforce unique opaque IDs, foreign keys including organization and ticket binding, transactions, optimistic version checks, idempotent investigation creation, encryption and bounded retention; handle concurrent membership revocation in the same trusted transaction or equivalent policy; audit sensitive access without recording secrets; and provide deletion, backups, migrations and recovery. Evidence stores only a reviewed sanitized reference with classification and retention metadata. Contracts, authorization and concurrency tests must exercise the actual deployed service and database, not this harness. No live customer data should be stored until these requirements and operator identity verification are satisfied.
