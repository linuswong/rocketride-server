# LoginLens

LoginLens opens on **Investigate a login issue**. Enter an exact email or Auth0 user ID and optionally the reported incident time, timezone, application, symptom and Jira request key, then review and approve the read-only checks. The supplied Jira key is not verified. The timezone defaults to the browser's timezone and can be changed to the timezone in which the incident was reported. The time is displayed in UTC; it can trigger older account-log page reads but is not sent for account AI analysis. The application is context, not a log filter. Without a time, the app reads one page of up to 50 events; with a time it can read up to five pages. Events can still be missing. Review the returned event timeline and the locally generated support handoff before copying it to an authorized ticket. The handoff includes the account identifier and reported context, is not automatically sent or saved, and disappears on refresh. Jira Service Management is the intended first support integration; it is not yet connected. An experimental node exists in this checkout and appears in local engine discovery, but its presence in a RocketRide Cloud workspace has not been verified.

After checks complete, an agent can update the reported application, symptom, problem category and unverified Jira key locally without repeating the checks. A previously edited customer reply is preserved and flagged for review. Changing the account or reported time requires a new proposal and checks. The updated details and handoff remain in memory only.

The optional reported sign-in problem category supplies fixed, human-review guidance for password, MFA, identifier and application-access problems. It is an operator report, not a diagnosis or evidence; it is included in the local handoff and does not trigger extra reads or recovery actions.

If the identifier is edited while the form contains reported details, LoginLens asks the agent to confirm that those details belong with the new identifier or clear them before proposing checks. Existing results remain unchanged until a new proposal.

Before approval, LoginLens shows the account and reported context captured in the proposal. Edits to the form do not change an existing proposal: the app flags those edits, and the operator can propose again to use them.

If the identifier could be interpreted as either an email or a user ID, choose its type before proposing the investigation. This prevents LoginLens from silently choosing the wrong lookup.

Email searches currently support the Auth0 node's unquoted ASCII address format. For an unsupported format, use a confirmed Auth0 user ID; the app cannot search that email directly with these tools.

After an email search returns one match, LoginLens checks the current profile's user ID and email before retrieving account logs or blocks. If the profile email is missing or differs, the investigation stops; use a confirmed Auth0 user ID to investigate further. A matching profile is not proof of authorization or of who attempted a login.

When indexed email search returns no match, the operator can explicitly check Auth0’s case-sensitive `users-by-email` endpoint. This can find recently updated profiles, but different capitalization may be missed. Selecting an account requires independent confirmation and a separate approval; LoginLens rechecks its current email before reading account logs or blocks. This requires the updated Auth0 node and has not been verified against a live tenant.

If the email search returns multiple distinct matching account IDs, the operator can review and select an ID to propose a new investigation. The operator must independently confirm the intended account and approve the new checks; selecting an ID does not grant authorization. Before reading logs or blocks, LoginLens rechecks that the selected profile still has the reported email. Proposing the selected account replaces the account investigation results but retains submitted-email checks separately; those checks do not establish that an event belongs to the selected account.

The report and handoff record that the account was manually selected from multiple email matches. This preserves the uncertainty for the next support agent; it is not an authorization or actor-identity check.

The timeline also labels returned MFA successes. Auth0 can emit MFA failure and success events while checking multiple OTP enrollments, so a failure alone does not establish that the sign-in failed. Returned events may be unrelated or missing; compare their times and the user experience. [Auth0 explains this behavior](https://support.auth0.com/center/s/article/auth0-logs-show-both-gd-auth-failed-and-gd-auth-succeed-during-mfa-login).

The Alerts page shows returned MFA failures, rejections and OTP rate-limit events separately from sign-in metrics and rule-based alerts. An agent can explicitly retrieve one selected MFA event and, if its ID, type and timestamp match the snapshot and it reports a usable user ID, prepare an account investigation. The profile is not checked until the new investigation is approved; an event ID does not prove who attempted sign-in or grant authorization. They do not establish the affected account or current block status. Account investigations also call out returned MFA OTP rate-limit events; consult [current Auth0 guidance](https://support.auth0.com/center/s/article/MFA-limits-for-OTP-and-SMS-failed-input) before advising a retry.

The account findings include returned MFA authentication failure and rejection events, linked to their log page. These are signals to compare with the reported issue, not proof of its cause. With explicit AI consent, counts for these event types are included in the identifier-free account analysis summary.

From a live event investigation, an agent can prepare an account investigation for a profile that was verified during the source checks. LoginLens presents the selected user ID as an incoming lead and records whether it was linked directly, by email, or both. The agent can use it in a fresh form, which clears the prior form fields while preserving an existing investigation result until a new proposal. It does not run account checks until a new proposal is approved; the lead does not prove who attempted the login or grant authorization. Existing account results remain visible until replaced by a new proposal.

When returned account events near the reported time include a failed login followed by a success with the same application name, the investigation and local handoff call out the sequence. A shared application name does not prove the events are related, and an Auth0 success does not prove application access.

For an email investigation with a past reported time, the operator can search tenant logs for that submitted email. The report and handoff show the requested UTC window and warn if it ends less than an hour after the reported time. The query uses Auth0’s `user_name` field; a different username or missing field will not match, and returned pages are not proof of complete coverage. If a returned provider page is full, the operator can explicitly request older pages, up to five pages total. The updated Auth0 node requires `read:logs`, checks returned identifiers and timestamps, and reports full pages or rejected rows. LoginLens preserves page provenance and excludes duplicate event IDs across returned pages; a failed or repeated page stops further reads and leaves earlier results available. Offset pagination, retention, indexing and missing identifiers can still hide events. A submitted email does not establish who initiated an attempt or which account was involved. The local handoff includes these results and their limits; AI analysis does not. The lookup has not been live-verified.

Operators can separately check brute-force protection records for the submitted email, even when no user profile was found. This read-only check requires the updated Auth0 node and `read:users`; it returns a count without IPs. A record does not establish who attempted login or whether a particular login is effectively blocked. Results appear in the local handoff, not AI analysis. The check has not been live-verified.

When proposing an email investigation, operators can opt in to either submitted-email check before approving the graph. The tenant-log option requires a past reported time. Approved checks run after the account checks using the same task; a potentially shared provider failure stops further optional reads and the app reports which were skipped. The checks remain available individually after the investigation.

If a later submitted-email search or protection refresh fails, the earlier successful result remains visible and is marked as potentially stale in the report and handoff. Further paging is paused after a failed search refresh until a new search succeeds.

The report and handoff show when the browser received each submitted-email log page and protection response. These timestamps use the browser clock; they are not provider timestamps or a guarantee that the underlying records were current.

The report and handoff give next steps based on the submitted-email checks, including a full-page warning and permission guidance. These are deterministic review prompts, not a diagnosis or proof of who attempted to sign in.

After an investigation, an operator can create an editable customer reply draft locally. The draft asks for missing context without copying the account identifier, ticket key or raw evidence. Review and copy it into the support system; LoginLens does not send or save it. The offline example is marked as fictional.

The updated Auth0 node stops an exact-email lookup if its provider search page is full or the requested result limit is exceeded. In that case, investigate with a confirmed Auth0 user ID. Search indexing may still omit an account even when a page is short; an email match is not an authorization check.

The account report and handoff show the oldest and newest dated returned events and the count within one hour of the reported time. Those are observations from the pages returned, not proof that the interval is complete or that missing events did not occur.

When an application name is reported, matching returned application names are marked in both the account and submitted-email timelines and in the handoff. Name matches are comparison hints: names can change or be shared and do not prove an event is related to the reported problem.

Each LoginLens app session uses its own Auth0 telemetry task identity, reusing that task within the session. This avoids reattaching to a task from an earlier session after configuration changes. Before reuse, LoginLens checks the stored read-only pipeline and connection settings against the bundled configuration; a mismatch stops the investigation. Changing environment values during an active session can still leave that session's task using its earlier values. Tasks have a 15-minute idle TTL, so separate sessions can temporarily run separate tasks.

Task creation and verification have bounded local waits. If one times out, LoginLens stops the account investigation and warns that remote work may still be running; the timeout does not cancel it and no automatic retry is made.

If the protection-record check reports a missing scope or unavailable feature, the app can continue the approved account-log page reads and reports the protection check as incomplete. A rate limit, authentication failure, service outage or unclassified protection-check failure stops additional page reads.

Incident times use the selected IANA timezone, initially the browser's timezone. If a clock change makes a local time occur twice, choose the intended occurrence; if the time did not occur, enter a valid time instead. The selected time is shown in UTC and the reported timezone is retained in the investigation and handoff. Accuracy depends on the reported timezone and the browser's timezone data.

The Overview dashboard shows a labeled offline example, including synthetic user inventory counts derived in part from the example login activity. Select a map cluster or a priority anomaly to review its time window and supporting events, then run all available checks to see one recommended action and inspect the evidence. The fixture checks run locally.

Consecutive successfully retrieved overlapping snapshots can show failed sign-in and supported MFA event IDs newly seen compared with the prior snapshot, across all applications. Late indexing and incomplete logs can affect the comparison; it does not establish when an incident began or identify all failures. Newly seen markers remain on returned events across comparable snapshots until the agent marks them seen. Marking seen does not resolve the event. Markers disappear if the event leaves the returned snapshot, a retrieval fails or is incomplete, windows cannot be compared, or the session ends; they are not a durable queue. This comparison is kept only in memory.

For an event-derived account lead, the investigation and handoff retain a bounded selected event ID, type and timestamp for traceability when these fields are valid. The event is a lead, not proof of the actor. For an event-derived account lead, the agent can opt to use the selected event’s exact UTC timestamp as the investigation time. The app labels it as an event time rather than a customer report, and still asks the customer for their reported time in the reply draft.

For an ordinary failed sign-in, **Check account lead** lets an agent explicitly read the event’s reported user ID or submitted username. The returned ID, type and timestamp must match the selected snapshot. A supported email can be carried into a separately approved account search when no usable user ID is present. A submitted email is not a matched account or proof of the actor, and the event-detail read requires `read:logs` and the updated Auth0 node.

Tenant events are snapshots. Optional auto-refresh requests a new read-only snapshot every five minutes while a monitoring page and browser tab are visible; it pauses elsewhere and stops on incomplete retrieval, a retrieval error or disconnect. Stopping does not cancel a request already running. It is off by default, stops when the app closes, and does not provide background monitoring or send notifications. On the Alerts page, select **Review event** for an individual failed sign-in to open an investigation; the selection itself does not run additional checks.

**Load tenant events** starts or reattaches to `src/auth0_telemetry.pipe`, a RocketRide task containing only a tools source and the read-only Auth0 node. It verifies the running task before requesting the selected window; loading and refreshing telemetry require no model credentials or AI provider. The query uses up to five pages of 100 records. A partial response remains usable and displays its reason. A short page means the query was exhausted, subject to the tenant's retention, indexing and concurrent changes. Changing to a longer window requires a reload. Sign-ups and protection events are separate from the sign-in failure denominator. Missing locations stay unmapped. Group keys are local to a retrieval. Rules and their default thresholds live in `src/lensRules.ts`. Live historical spike and rate comparisons are suppressed until coverage can be independently verified.

Overview also lists other returned tenant event types separately, including API reads and client-credentials exchanges. These do not contribute to sign-in metrics or anomaly rules. The list uses sanitized event type, time and application fields, and is subject to the same retrieval limit and time window.

Loading tenant events does not retrieve the user inventory. Live total, active and inactive user KPIs remain unavailable; sign-in events do not establish registered-user totals.

For sustained monitoring, evaluate Auth0 Log Streams and an appropriately authorized, tenant-isolated destination. No stream or persistence is configured by this application. Auth0 may omit user identifiers from failed logs, limiting account and spraying detection. Account follow-ups use IDs returned by verified event reads; browser checks do not establish server-side tenant membership or an independent authorization boundary.

On a tenant anomaly, **Run all available checks** verifies a selected event, reads both protection settings, queries the anomaly and equal-length prior windows, and checks a recent page of the selected event type when supported. For failures, it also counts source groups and retrieves one representative event from the largest group to compare its IP against Auth0's brute-force and IP-throttling allowlists. The source IP is visible in the inspector, is not sent to a model, and is not persisted. The check needs `read:logs` and `read:attack_protection`; it requires the updated Auth0 node. An allowlist match does not prove corporate ownership, and a nonmatch does not rule it out. ASN lookup is not configured. Missing or malformed source data, unavailable settings and incomplete history remain explicit.

The source check also compares the event IP with positive IP ranges in the first page of active authentication and tenant ACL rules, using `read:network_acls`. It reports the number of rules with a matching range, not their names or ranges. The trusted-IP and ACL comparisons each retry once when Auth0 supplies a retryable rate-limit interval of at most 30 seconds; persistent or longer limits stop dependent reads. A match does not establish that the full rule applied, its action, corporate ownership or an ASN; other conditions, exclusions and priority are not evaluated. Partial pages and unavailable access remain explicit. Tenant ACLs depend on the Auth0 plan, and this check has not been verified against a live tenant.

When tenant-wide history returns some events before an Auth0 error, the investigation retains the events and marks the check partial. A rate limit, authentication failure, timeout or service failure stops later account and agent follow-up reads; a missing-scope result identifies the required permission. Reads already in flight may still complete.

The same shared-failure stop applies during account lookup, profile, block and log reads. Already verified event-to-account matches remain visible, and the agent receives the stop category and any reliable rate-limit interval. A missing scope for one account operation is reported separately, so checks using other scopes can still proceed.

For each linked account, the inspector and agent receive counts of directly linked selected events by Auth0 failure category. Email-derived candidate links are excluded from those direct counts. A wrong-password event alone does not show that credentials are stale or identify who submitted the attempt.

When Auth0 supplies JA3 or JA4 TLS fingerprints on selected source events, the investigation counts distinct fingerprints and the largest matching group for each type among verified events from that source. Raw fingerprints stay in the browser session and are not sent to Gemini. When a node omits the JA4 field, JA4 coverage for those events is unknown. A shared fingerprint can reflect common client software and does not prove a common actor, corporate ownership or malicious intent. This requires the updated Auth0 node and `read:logs`. If an older node rejects the fingerprint option, the app retries without it and continues account correlation, while reporting the missing fingerprint capability.

When Auth0 reports a missing scope on a required read, the deterministic recommendation can name the corresponding Management API permissions and ask for a rerun. The updated Auth0 node automatically refreshes a cached read token after a missing-scope response, at most once every 30 seconds; wait 30 seconds after changing permissions before rerunning. When that prerequisite is selected, it takes precedence over an AI recommendation.

If a required read or source comparison reports a rate limit, timeout, authentication failure or service outage, the agent does not schedule additional Auth0 reads around that stop. In the absence of a verified account block or missing permission, the deterministic recommendation identifies the prerequisite for rerunning the investigation instead of presenting a speculative fix. When every relevant rate-limited response includes a bounded retry interval, the recommendation uses the longest reported interval; otherwise it does not invent a wait time.

The agent also rejects a small set of generic conclusions such as “review the pattern” and manual IP-review instructions after source inspection, then asks for another check, a specific supported action, or an explicit insufficient-evidence conclusion within the existing request limit. If the model repeats generic conclusions and a bounded read-only candidate remains, the app runs one and asks the model to reassess. These are limited wording checks; they do not establish that an AI recommendation is correct or that corporate ownership can be determined.

For recognized recommendations to remove an account block, the agent requires a cited verified account block linked to the largest source group and checks the type when the recommendation specifies administrative or brute-force blocking. This is a narrow safeguard, not a general proof that model claims or proposed actions follow from the evidence.

**Automatic AI follow-up** is off by default and must be explicitly enabled before the checks run. It sends event categories and timestamps plus allowlisted aggregate results, including anonymous per-account and submitted-identifier attempt counts and fixed error categories such as missing permissions or rate limits, to Gemini, excluding account IDs, submitted usernames, source IPs and raw responses. In each round the model can select an application-generated, evidence-bound read-only candidate: another selected event, a recent event type, a preceding 24-hour window, another selected source group and its account checks, or an older log page for a verified account when its previous page was full. It receives each result before choosing again and returns one recommendation with references to completed checks. Account-history follow-ups can inspect up to four additional 20-event pages per account, deduplicating event IDs and verifying the account and source for returned failures; offset pagination can still miss events during ingestion. The app rejects invented or repeated candidates, arbitrary tool parameters and invalid citations. One run uses at most 20 model requests and 39 additional checks; each request starts a fresh tool-free task configured for one provider attempt, and may incur charges. A timeout may leave a remote task running, so this is a request limit, not a billing guarantee. Invalid decisions receive up to two automatic correction requests within the same limit; the loop stops if those fail, the provider is unavailable, the evidence changes or the request limit is reached. It retains recorded checks and a deterministic fallback. It cannot guarantee a root cause or fix; AI claims and proposed changes require human review. The offline example uses fictional local responses for all rounds.

For each older history page, the page read and event-detail verification each retry a short Auth0 rate limit once when Auth0 supplies an interval of at most 30 seconds. Details are read in batches of four; a persistent limit or shared service failure stops the remaining reads, preserves verified results, and reports unchecked events to the agent and the inspector.

When a verified account has a full history page and an eligible older page remains, the app follows it before the first Gemini request, subject to the shared 39-check follow-up limit. Pagination remains bounded and cannot establish complete retention or indexing.

When accounts or unresolved submitted identifiers show repeated failures, the app follows the other selected source groups before its first Gemini request, up to the 39-check follow-up limit, including when an account in the largest group is blocked. Repeated identifiers do not establish a verified account or who made the attempts. The app shares that limit between source comparisons and older account pages, and examines shallower pages across accounts before deeper pages. At most 20 ranked source groups can be investigated. The model and summary are told when the follow-up limit leaves eligible checks unrun or the selected evidence contains more than 20 source groups, including if the model is unavailable. It rejects recommendations to change protection settings unless they are conditional on confirming abuse or applicable policy; shared sources and repeated failures alone do not prove malicious activity.

When repeated attempts are found, the app runs remaining available evidence-bound checks within the shared limit before asking Gemini to recommend an action. If a later follow-up discovers repetition, it runs the remaining checks before the next model request.

When a verified account linked to the largest source group is currently blocked, the single displayed recommendation prioritizes the recorded block over a different model suggestion: an authorized administrator can clear it after confirming it is no longer needed. The block may not explain every failure, and the app does not perform the change.

For each checked secondary source, the app counts accounts directly linked to events in both that source and the largest group, requiring a verified profile in each. The investigation can show those account IDs; Gemini receives only the count and check references. These counts cover checked events and do not identify who made the attempts.

The source inspector groups verified events by their reported application ID and name and shows which were directly associated with each resolved account. Names need not uniquely identify an Auth0 application; missing IDs and names are unknown. The event application is not necessarily the application configured for LoginLens. The ID option uses `read:logs`; if an older node rejects it, the app retries without it and retains other available checks. For up to five reported application IDs per source, the app also reads the current application type, token authentication method and selected grant flags using `read:clients`. It requests no client secrets. Missing permission, unavailable checks and unchecked IDs are reported; current settings do not prove the cause of an earlier event. Gemini receives anonymous references and allowlisted settings, not application IDs or names.

For a directly linked verified account, the app also checks whether the returned recent user-log page contains a successful login after that account's latest selected failure. It checks up to three distinct candidates, newest first, by event ID, account, type and timestamp, stopping after the first verified success or a shared Auth0 failure. When available, it compares the success event's IP and application ID with that failure. Even a same-source, same-application success may use a different device or credential; a missing success in the returned page does not establish that none occurred.

Model citations normally name completed checks. An event reference is converted to a check citation only when exactly one successful event check verified that reference; ambiguous or unverified references are rejected. The agent also rejects certain unqualified claims that no failures or suspicious activity occurred and asks the model to limit its statement to checked evidence; this wording check cannot detect every unsupported inference.

The investigation compares successful and failed sign-ins from the largest source within the selected window, using the loaded snapshot rather than assuming complete tenant coverage. It then automatically refetches up to 50 selected failures in that source group, verifies each event's ID, time, type and source, and groups the returned account IDs. Selected event reads run in batches of four. Completed reads that report Auth0 unavailable receive one retry when no other response in the batch reports a rate limit, timeout, authentication failure or missing scope; once during this stage, explicitly retryable rate-limited reads can also retry after an Auth0-supplied interval of at most 30 seconds. Persistent or longer limits and service, timeout, scope, or authentication failures stop the remaining selected reads and leave them marked unchecked. After a rate limit, service failure, timeout, or authentication failure, dependent account reads do not start; already verified event evidence remains available. When the ID is missing but `user_name` is email-shaped, it searches for a unique exact email match and verifies the returned profile; those links are labeled email candidates, not proof of who initiated the attempt. Repeated activity is counted separately for verified profiles with direct event links, email-linked candidates, and unverified profiles; the agent receives the same distinction. Ambiguous or missing matches remain unresolved, and available unresolved usernames are displayed with attempt counts. For up to 20 identified accounts it verifies the profile, checks administrative and brute-force blocks, and reads up to 20 recent events. It refetches up to 400 recent failures (at most 20 per checked account) to verify their account and source before counting repeated same-source activity. Those reads run in batches of four. Once during the recent-detail stage they retry rate-limited reads when Auth0 supplies a retryable interval of at most 30 seconds; persistent or longer rate limits, availability failures, timeouts, missing scopes, and authentication failures stop further detail reads. Up to four extra requests may be used for that retry, and unattempted counts remain visible per account. This proceeds in stages without another prompt; failures, missing identifiers, full pages and limits remain visible in the source-account inspector. Account IDs, submitted usernames and IPs are held in the current browser session and are not sent to a model. These checks require `read:logs`, `read:users` and `read:logs_users`; protection comparisons additionally require `read:attack_protection`. Results are read-only and do not prove a compromised account or root cause.

LoginLens has six sections: **Overview** for headline sign-in metrics, the activity map and the trend; **Map** for the full-size activity map with region and anomaly details; **Analytics** for sign-in trends, failure categories and unusual activity by rule; **Investigations** for evidence and graphs; **Alerts** for rule-based anomalies, listed separately from ordinary failed sign-ins; and **Integrations** for engine, Auth0 and AI provider status and the detection thresholds. The selected time window and loaded event snapshot are shared across Overview, Map, Analytics and Alerts. Metrics and statuses show "—" or "Not loaded" until data is available; no period-over-period changes are shown because prior-period data is not retrieved.

## Architecture and limitations

The App Builder scaffold exposes one React descriptor to the RocketRide shell. Telemetry and approved graph and account reads use the verified Auth0-only `src/auth0_telemetry.pipe`, which contains no model or agent. It uses metadata-level pipeline tracing. React never calls Auth0 directly. The Auth0 node uses an M2M Management API client on the engine. No write operation is exposed in the app and `allowWrite` is false.

The application uses the supported `client.tool` API to invoke a named, allowlisted `tool_auth0_1` read operation directly. Every request makes new calls; it does not use model text or earlier conversation as tool evidence. An exact-email helpdesk search retrieves `search_users`, then `get_user`, followed by concurrent `get_user_logs` and `get_user_blocks` for a single matching user. The console displays each current response, request arguments, status, and returned identifiers; older responses are marked as previous evidence. Empty, failed, or malformed responses do not establish a diagnosis. For a named operation, the requested tool is called directly or the request fails clearly. The `search_logs` tool is tenant-wide and cannot filter by email; use an exact-email helpdesk search for user-specific logs. Requests requiring an ID must include it as, for example, `user_id: auth0|...`.

The optional account diagnosis uses a fresh, isolated Gemini pipeline. Model explanations are unverified and must be compared with the returned evidence. No write operation is exposed.

## Sign-in investigation graph

Open **Investigations → Investigate an account**, enter an exact email or Auth0 user ID, and select **Propose investigation**. Review the graph and approve the checks. The graph reports the real start and completion of each direct SDK call; it does not show internal Auth0 request or retry progress. Select a node or use the check list to inspect findings, sanitized inputs, validated output and available trace. Expandable JSON contains the filtered output, not the original response. The overall evidence summary remains below the graph. Pan, zoom, and fit controls are available in the graph. Proposing another investigation starts a fresh graph. Results and in-progress work remain available when switching app sections, but are held only in memory and are not persisted or audited; reloading or closing the app loses them.

The workflow searches for a unique exact match, verifies the returned profile ID, then requests user logs and brute-force block records concurrently. Zero matches, multiple matches, failed searches and mismatched profiles stop dependent checks. When an incident time is supplied and a log page is full, it requests older pages until a short page, a full date-ordered page reaching one hour before the reported time, an error, a repeated page or the five-page limit. A potentially shared or unclassified block-check failure stops subsequent log-page reads; a missing scope or unavailable feature for that check does not prevent independently scoped log reads. It deduplicates returned event IDs, retains successful pages if a later page fails, and shows the stop reason and any error. Offset pagination can miss events during ingestion; the stopping rule, a short page and a reported match do not establish complete coverage. An older node may reject the `page` argument, in which case the first page remains available and the failure is reported. Empty logs mean insufficient evidence; a successful block lookup with records is a security finding, not a failed tool call. No writes are available. Additional tenant-wide settings, roles and permissions are not fetched automatically because they do not by themselves explain a specific sign-in.

The account diagnosis is optional. After checks complete, separately authorize and select **Generate AI analysis** to send check types, bounded counts, account verification and block flags, fixed error categories and the account-history stop status to the configured model provider. Account IDs, emails, application names, raw events, timestamps and reported case context are excluded from that payload, though the remaining facts may still be sensitive. Counts exclude duplicate event IDs across pages and report how many IDs were missing. It uses a newly started, verified tool-free pipeline (`synthetic_investigation.pipe`) and is terminated afterward; it does not issue additional Auth0 calls. The app requires one to four references to successful supplied checks and links them to the corresponding inspector page. A valid reference does not prove that the generated claim follows from the evidence; compare every claim to the inspector. If the model is unavailable or returns invalid references, the graph retains the checks and reports the analysis failure. Tool execution states reflect frontend SDK request boundaries, not engine trace events; the graph does not expose backend retries or streaming model tokens. The separate anomaly follow-up uses the different payload and controls documented above.

Run the deterministic workflow tests with `node --experimental-strip-types --test apps/auth0-operations-ui/test/investigation.test.mjs` from the repository root. These mocked tests do not verify a live engine, visual layout, or actual parallel execution behavior of the remote engine.

## Prerequisites and credentials

- An explicitly authorized **non-production Auth0 tenant** and designated test user; never run live tests against production.
- A RocketRide engine containing the checked-out Auth0 node, Wave agent, internal memory, chat, answer response and Gemini LLM node. The experimental node and model must be available to the target engine. An engine connection alone does not prove this.
- In RocketRide's secure environment configuration set `ROCKETRIDE_AUTH0_DOMAIN`, `ROCKETRIDE_AUTH0_CLIENT_ID`, `ROCKETRIDE_AUTH0_CLIENT_SECRET` and `ROCKETRIDE_GEMINI_KEY`. The bundled pipelines contain only variable references. Do not place actual secrets in source, manifests, browser storage, logs or pipeline files. The configured Gemini model must be enabled for the API key.
- For the AI provider, set `ROCKETRIDE_GEMINI_KEY` to your Google Gemini API key in the environment of the RocketRide engine running the tasks. Restart or stop and start existing investigation tasks after changing the pipeline or key so they pick up the current configuration. The app's AI pipelines select the `models-gemini-3-1-flash-lite` profile.
- Grant the read-only Auth0 M2M client only necessary Management API permissions: `read:users`, `read:logs_users`, `read:logs`, `read:connections`, `read:clients`, `read:attack_protection`, `read:roles`, and, if using organization tools, `read:organizations` and `read:organization_members`. More detail and qualifications are in the node README. Keep `allowWrite` false.
- Node.js and pnpm, with server-matched `.rocketride/client/rocketride.tgz` and `.rocketride/shell/shell.tgz` vendored by the connected App Builder. The local engine serves these under `/client/shell` and `/client/typescript`; if `/client/shell` returns 404, build or pack the shell before vendoring. In the monorepo, workspace overrides resolve shell and client imports to the source packages instead, so rebuild stale SDK declarations with `pnpm exec tsc -p packages/client-typescript/tsconfig.types.json`.

## Preview and verification

Open `auth0-operations.rrapp` in the RocketRide App Builder with the workspace connected to the intended engine. The App Builder installs dependencies with pnpm and starts the Design preview. Check its watch and error panels and enable Inherit Auth if appropriate. `pnpm run build` from the app folder checks TypeScript and produces a local bundle, but it does not prove that the shell serves or runs it.

For this Windows monorepo, after building the engine and its shell/client artifacts, start the engine in one PowerShell window and the local preview in another:

```powershell
Set-Location dist/server
.\engine.exe ai/eaas.py
```

```powershell
node packages/client-typescript/dist/cli/packages/client-typescript/src/cli/rocketride.js app dev apps/auth0-operations-ui --uri http://127.0.0.1:5565 --no-install --no-auth
```

Open the printed preview URL and connect using your local engine credential. The preview port can change if the configured port is occupied. `--no-install` assumes the root workspace install has already succeeded. To build the app, run `pnpm --dir apps/auth0-operations-ui run build` from the repository root.

If the CLI reports `ECONNREFUSED` on port 5565, start the engine and wait for its startup message before starting the preview. Run both commands from the directories shown above. If loopback access is blocked by the execution environment, allow local networking. Another App Builder preview can occupy port 3821; use the URL printed by the CLI after any port bump. Wait for the build's `ready` message as well as the URL, then check the shell in a browser. The generated proxy wrapper belongs to its running preview session; leave other files in `.rocketride` intact.

The SDK's `client.deploy.verifyApp('apps/auth0-operations-ui')` performs the local manifest/packaging check. It does not validate the pipeline, build, engine compatibility, tenant, or tool calls. Run `node --experimental-strip-types --test apps/auth0-operations-ui/test/operations.test.mjs` from the repository root with Node 22 for the focused parsing and pipeline guard tests. Run the Auth0 node tests with `python -m pytest nodes/test/tool_auth0 -q` in the repository's configured Python test environment. These tests are mocked and are not a live integration test.

Before a live test, confirm the tenant and user are authorized, then verify the pipeline and inspect its trace for `search_users`, `get_user`, `get_user_logs`, and `get_user_blocks` and their actual return values. Record only sanitized pass/fail evidence; do not save user identifiers, event contents, tokens, or raw responses. See `nodes/test/tool_auth0/LIVE_TESTING.md` for precautions. Do not change users or security configuration. A local shell test on 2026-11-16 used the user-designated development tenant and test user. The trace showed the agent, Auth0 node, and answer node; separate direct read-only calls matched the displayed profile, recent-event, and block-state claims. Direct SDK tool-call trace begin/end labels identify the named methods; metadata-level traces do not independently prove the contents of their results. One earlier attempt stopped after a partial answer, so the agent must not be relied upon to complete every requested call or to interpret every result correctly.

### Geographic map

LoginLens bundles MapLibre GL JS (BSD-3-Clause) and the `world-atlas` Natural Earth 1:110m country polygons. Natural Earth data is public domain; attribution is displayed on the map. The style and boundaries are local, so no map service, API key, or external tile requests are needed. Deployments must allow WebGL and MapLibre's blob-based worker under their browser Content Security Policy (`worker-src blob:`). The bundled overview polygons are generalized and omit some small islands; border and offshore geolocation can be unassigned or approximate. State/province boundaries are not included. Authentication locations are approximate network origins, and density is activity, not a finding of malicious behavior. Country account counts include only identifiable account groups and may undercount accounts where identifiers are missing.
